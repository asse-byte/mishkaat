Chapter 13Verification and Quality Assurance

13.1 Testing philosophy

The test strategy is behavioural rather than unit-oriented, and it rests on three commitments that differ from conventional practice.

Commitment 1 — test for leakage, not for success In an isolation suite, a 200 response is not a failure; a 200 response carrying another party's data is. Each assertion asks whether the payload contains something that does not belong to the caller. A suite that only checks status codes would have passed against every one of the seventeen leaks that motivated the scope module.
Commitment 2 — every assertion is verified to fail Each test was run against the defect reverted, to confirm that it actually fails. An assertion that passes both with and without the fix protects nothing. This is stated explicitly in the headers of the regression and performance suites.
Commitment 3 — a new endpoint touching student or circle data is added to the isolation suite in the same commit This is the rule that keeps the boundary from eroding endpoint by endpoint, which is how it eroded before.

Suites run against a live MongoDB. Each creates a temporary database, exercises the application layer directly (the startup routine, routers and scope helpers are imported and called), and drops the database at the end, so production data is never touched.

13.5 Coverage gaps

Stated plainly, because a report that claims complete coverage is not credible:

  • No automated front-end tests. No component, integration or end-to-end browser suite exists. Interface behaviour is verified manually.
  • No continuous integration pipeline is committed. The gates above are documented as procedure; they are not enforced automatically on every push.
  • No load or performance testing. The index strategy and the bulk-query patterns are reasoned rather than measured; no figure for concurrent users or p95 latency is claimed anywhere in this report.
  • No formal coverage measurement. The suites target authorisation boundaries and business rules by design; ordinary CRUD paths are covered only where they intersect those boundaries.
  • The forecast has not been validated against outcomes. What is tested is that quality affects the prediction — not that the prediction is accurate. Accuracy requires a season of real completions (§16.2).

Chapter 14Deployment and Operations

14.1 Deployment topologies

14.1.1 Docker Compose (recommended)

  1. Copy backend/.env.example to backend/.env and complete every field; create a top-level .env with the MongoDB root and application credentials and the database name.
  2. Place the TLS certificate and key in ops/tls/ and set the real hostname in ops/nginx.conf.
  3. Build the front end (npm run build) so that Nginx has static assets to serve.
  4. docker compose up -d --build.
  5. Watch the first boot: if INITIAL_ADMIN_PASSWORD was not set in a development environment, the generated password is printed once.

The stack gives, by construction, a topology in which Mongo and the application are unreachable from the internet: neither publishes a port, and both sit on a network declared internal: true. The application container additionally runs with a read-only root filesystem, a tmpfs at /tmp, all capabilities dropped and no-new-privileges.

14.1.2 Single VPS with systemd

The application is installed under /opt/mishkaat with its environment file at /etc/mishkaat/mishkaat.env (mode 600, owned by root). Three units are supplied: the API service, a one-shot backup service and a timer that runs it daily. The API unit runs under DynamicUser with NoNewPrivileges, no write access outside /tmp, no access to kernel tunables, and an outbound network allow-list restricted to localhost — so the process can reach MongoDB and nothing else.

14.2 Configuration reference

The complete environment variable reference is Appendix A. Three settings deserve emphasis here:

  • TRUST_PROXY — must be true when, and only when, a reverse proxy under the operator's control sets X-Forwarded-For. False behind a proxy means five wrong passwords from one person lock out everybody; true without a proxy means a client can forge the header and evade the limiter entirely.
  • PII_ENCRYPTION_KEY — must be in a secret manager and backed up. Losing it destroys the encrypted fields permanently.
  • SEED_DEMO_DATA — must remain false in production, and its absence must be verified during onboarding rather than assumed.

14.3 Backup and disaster recovery

mongodump --archive --gzip ──┐ ├──► gpg --encrypt ──► /var/backups/mishkaat/ │ mishkaat-.archive.gpg (mode 600) plaintext NEVER touches disk ┘ │ ├──► retention: last 30 days (RETENTION_DAYS) └──► optional: rclone copy → off-host remote restore.sh ──► gpg --decrypt ──► mongorestore (staging host, private key)

The design point is the key split: a backup-only GPG key pair is generated, and only the public key is installed on the production host. The private key stays with the operator, off-host, so a compromise of the server yields encrypted archives that the attacker cannot read. The timer fires daily at 03:17 UTC. A restore drill is documented as a requirement to be performed before it is needed, not after.

14.6 Scaling considerations

Table 14.3 — Scaling posture
DimensionCurrent position and next step
Application processesFour Uvicorn workers behind Nginx. Scaling horizontally is safe because no correctness-bearing state lives in process memory: rate limiting, notification fan-out and counters are all in MongoDB. The one in-memory item is the forecast model cache, which is per-worker and explicitly advisory.
DatabaseA single MongoDB instance. The indexes cover every hot path. A replica set is the next step, both for availability and to move heavy analytical reads to a secondary.
Analytical readsMetrics are computed on read. For a large centre the circle overview and leaderboards load history in bulk, but the cost still grows with volume. If it becomes a constraint, the correct response is a cached snapshot with an explicit computation timestamp — not a stored derived value that silently diverges from its sources.
File storageGridFS. Files are small and few; if attachment volume grows, an object store with signed URLs is the migration, at the cost of leaving the single-backup property behind.
Live notificationsThe stream polls the database, which is correct across workers and requires no broker. At high connection counts a publish/subscribe layer would reduce read load — at the cost of the property that makes the current design robust.
