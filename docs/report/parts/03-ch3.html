Chapter 3Stakeholders and Users

Mishkaat defines six user roles. The role is not merely a label used to hide menu items: it is the input to a scope-resolution function that decides, for every query the system runs, which rows the caller may see. This chapter defines the roles, the scope model that binds them, and the deliberate exceptions where a role sees slightly more than its data scope would strictly allow.

A role decision worth stating plainly The centre manager reads everything in his centre but records neither recitation nor attendance. The reasoning is not technical: recording a recitation is testimony about a session the recorder attended. The manager corrects errors by editing and deleting, but does not create a record attesting to a circle he was not in. The same rule removes the manager from competition scoring: he appoints the panel and approves its result, but he does not enter marks. This is enforced server-side by scope.teacher_only(), not by hiding a button.

3.1.1 The external teacher

A centre may employ teachers who are not circle teachers: a language teacher, a visiting tajwīd specialist, an administrator who also teaches. These are recorded with teacher_type: "external" and no system account is created for them: a request that supplies a username or password for an external teacher is rejected with HTTP 400, and converting an existing circle teacher to external closes their account and invalidates their sessions. The reason is that an account in this system opens students' recitation, attendance and performance data — that is the trust of the circle, not the trust of a visitor giving a lesson in a subject. Someone who neither hears recitation nor marks attendance needs no door.

3.2 The scope-resolution chain

The teacher's scope is not stored on the user document. It is resolved at request time by walking a four-link chain, so that reassigning a circle immediately changes what a teacher can see, with no synchronisation step and no stale permission row:

users._id the authenticated account │ ▼ teachers.user_id the teacher record bound to that account (active only) teachers._id │ ▼ halaqat.teacher_id the circles this teacher currently teaches (active only) halaqat._id │ ▼ students.halaqah_id the students inside those circles students._id

Two properties of this chain are load-bearing:

  • A teacher with no linked record, or with no assigned circle, has an empty scope and sees nothing. This is correct, not a defect: in the absence of an assignment the default is denial, not permission. The students screen says “no circle has been assigned to you yet” rather than showing an unexplained empty list.
  • An empty scope is represented as None, never as an empty filter. In MongoDB, {} matches every document. A function that returned {} for “nothing is visible” would return the whole collection — a total inversion that reads as correct code. Every scope helper in the module returns None for the empty case and every caller treats None as “return an empty list”.

Student and guardian ownership resolves differently and equally deliberately. A student is matched to a record by students.user_id or by phone number; a guardian by students.parent_user_id or by phone. Never by name. A user can edit their own display name from their profile; matching on the name would mean that renaming yourself to a classmate's name opens that classmate's file, grades and fees. Name is not an ownership identifier.

3.5 The communication chain

Messaging is not an open directory. Each party addresses only those directly above and below them, which keeps system administration out of direct contact with children and their guardians:

system admin ⇄ centre manager ⇄ teacher ⇅ student / guardian
Table 3.4 — Permitted message audiences
SenderMay address
admin / super_adminCentre managers only — not teachers, students or guardians
center_managerThe teachers of their centre, their students, their guardians, and system administration
teacherTheir centre manager, and no one else
student / parentReceive and reply; do not initiate broadcasts

The permitted audiences are read from GET /api/messages/audiences and are never hard-coded in the front end. A client-side list diverges from the server rule at the first change, and then offers the user an option that returns 403 when pressed. Attachments are downloaded with the permission check applied to the message, not to the file: were the file identifier alone sufficient, anyone who guessed one would read another centre's document.

3.6 Deliberate exceptions to the scope rules

Four places open slightly more than the strict data scope. Each is a deliberate decision with a narrow, documented boundary.

Table 3.5 — Sanctioned scope exceptions
#ExceptionBoundary and reason
E1Leaderboard scope is the circle, not the self A student's leaderboard was previously built on his own data scope — a single row — producing “rank 1 of 1” on all four boards. A leaderboard with no peers is not incomplete; it defeats its purpose. The leaderboard query therefore returns the student's circle: peer names, ranks and metric values. These are the aggregate figures written on a blackboard in any mosque. It opens no files: reading a peer's record still passes through check_student_access and still returns 403.
E2Competition results are public within the centre A student sees all branches and everyone's ranking. A competition is a declared public event whose results are read aloud.
E3Circle ranking is visible to teachers GET /api/halaqat-overview/ranking returns aggregate figures plus circle and teacher names — and not one student name from another circle.
E4Competition records are readable by every teacher of the centre A teacher reads his centre's competitions and their results; only scoring is restricted to the appointed panel. Previously a non-judge received 403 and therefore could not know his centre held competitions at all.
What none of the four exceptions opens The student file. Whoever sees a peer's name on a leaderboard or in a competition result cannot open that peer's record: the request returns 403, and that assertion is part of the isolation test suite (§13.3).
