1.1 Project identification

The system documented here is named Mishkaat — Arabic المشكاة, the niche in a wall that holds a lamp. The name is taken from the Qur'anic image of light held in a recess so that it illuminates the room around it; the intent of the naming is that the software should hold and make visible what a memorisation circle is already doing, rather than change the pedagogy itself.

1.2 Background and motivation

A Qur'an memorisation centre (دار تحفيظ or مركز تحفيظ) is an educational institution organised around halaqāt (حلقات, singular حلقة) — study circles in which a small group of students sits with one teacher, the muhaffiẓ (محفّظ, literally “the one who causes memorisation”). The core daily event is tasmīʿ (تسميع): a student recites a passage from memory and the teacher listens, corrects, and forms a judgement of the quality of the recitation.

This model has three characteristics that make it difficult to administer at scale:

  1. The primary record is oral and ephemeral. The teacher's judgement of a recitation — where the student hesitated, what kind of error occurred, whether the passage is secure — exists in the teacher's memory and, at best, in a shorthand mark in a paper notebook. It is not comparable across students, across teachers, or across time.
  2. Responsibility is distributed but accountability is centralised. The teacher owns the circle; the centre manager answers for the centre's academic results and its finances; the parent pays fees and expects to know whether the child is progressing. These three parties rarely see the same information.
  3. The unit of progress is contested. “How much has the student memorised?” is usually answered in ajzāʾ (أجزاء, the thirty parts of the Qur'an), but two students who have both “finished five parts” may differ enormously in the security of that memorisation. Quantity is recorded; quality is not.

The consequence is a documented set of operational failures: enrolment registers that drift out of date, fees that are collected twice or not at all, teachers' salaries paid twice in the same month because nothing records that they were already paid, absence that parents learn about weeks later, and — most importantly for the academic mission — no defensible answer to the question “when will this child finish, and is he progressing or only attending?”

1.3 Problem statement

The problems Mishkaat is designed to solve are enumerated below. Each is stated as an observed failure of the status quo, paired with the design response that the system makes. The pairing is important: each mechanism in the system exists to answer a specific named failure, and Chapter 4 traces each back to a numbered requirement.

Table 1.2 — Problem–response matrix
#Observed problemConsequence in practiceResponse in Mishkaat
P1 Recitation quality is unrecorded and incomparable A teacher's note “made mistakes” cannot be compared between two students, nor for one student over a term. Free-text error notes are written differently by every teacher. A closed, four-class weighted error taxonomy (§9.2). The teacher tags each error by type on a phone during the circle; the severity weight lives in one place in the code and is never stored alongside the error.
P2 Progress is measured only by quantity Two students with identical page counts receive the same projected completion date, even when one misses half the sessions and errs on every page. A three-feature regression model (momentum, weighted error density, attendance rate) trained on the centre's own history, so that recitation quality affects the projected date (§9.4).
P3 A single ranking demotivates exactly those who need encouragement A student who appears last on one composite leaderboard every week learns to ignore it entirely. Four independent leaderboards — momentum, precision, consistency, review depth — so that the slow student who never misses a session leads the consistency board (§9.5).
P4 Everyone in a centre could see everyone's data In the pre-حلقة-scoped version of this system, a circle teacher could read every student in the centre — names, guardians' phone numbers, recitations, attendance, performance metrics, projected completion dates and fee records — and could log a recitation for a student who was not his. Seventeen distinct leaks from one root cause. A four-level scope model (system / centre / circle / self) defined in a single module, app/scope.py, that every endpoint queries; plus one mandatory ownership gate, check_student_access, for any endpoint taking a student_id (§10.3).
P5 Administrative acts could be performed twice Double-clicking “save” produced two recitations for the same day, two salary payments for the same month, two fee records for the same month. The duplicate salary is real money leaving twice; the duplicate recitation corrupts every derived metric and forecast. Three uniqueness guards enforced with HTTP 409 and, where possible, with unique database indexes rather than code-level checks (§11.9).
P6 Every administrative act is fallible, but nothing could be corrected A fee entered against the wrong student, a salary with a wrong amount, an attendance mark on the wrong child — with no correction path, staff work around the system and the records stop reflecting reality. Edit and cancel paths for every administrative record, with a strict distinction: money is voided, never erased — marked voided with a written reason and an actor, and excluded from every total (§11.7).
P7 Absence notification is a broadcast into the void An absence alert delivered only over a live connection reaches a parent who happens to be looking at the application at 06:30 on a weekday, i.e. almost never. Every notification is persisted to the database first and streamed second, so the database is the single source of the stream and a notification survives both worker restarts and offline parents (§11.4).
P8 Financial and permission history was not defensible Where a dispute arises over a payment or a permission change, an ordinary log can be edited by anyone with database access. A SHA-256 hash-chained audit log with atomic sequence numbers, explicit gap marking, and a permanent-record class of actions that is never purged (§10.7).
P9 Supervisory bodies cannot tell an active centre from a large one A centre that enrolled a hundred students and then abandoned the system outranks a centre with twenty students working daily, because the ranking counts head-count. A centre activity index that measures transactions per student over a time window rather than absolute size (§9.6).
P10 Review (المراجعة) was unmanaged A single hard-coded weekly review table was displayed to every student regardless of how much each had memorised, and its “done” marker compared a Juz' number to an āyah number — so reviewing verse 3 of any sūrah marked Saturday complete, permanently. A daily review portion derived per student from what that student has actually memorised, at a rate the teacher sets, computed from the date rather than from stored state (§9.6).

1.4 Aim and objectives

Aim. To deliver a single, auditable, multi-tenant system through which a Qur'an memorisation centre can run its academic, administrative and financial operations, and through which the academic quality of memorisation — not merely its quantity — becomes measurable, comparable and explainable to the people who need it: the teacher, the manager, the student and the parent.

1.5 The proposed solution

Mishkaat is a three-tier web application. A React single-page application, installable as a Progressive Web App, communicates over HTTPS with a FastAPI back end; the back end alone speaks to a MongoDB cluster that is never exposed to the network. The application layer is decomposed by domain — one router per business area — over a set of cross-cutting modules that hold the decisions no single domain should own: authentication, authorisation scope, personal-data encryption, audit chaining, performance metrics, forecasting and motivation.

Two design commitments distinguish this system from a conventional school-administration product and recur throughout this report:

Commitment 1 — derived values are never stored Every performance metric, every leaderboard position and every forecast is computed at read time from the recitation and attendance records that produced it. A stored derived value drifts away from its source rows at the first correction or void, at which point a student's leaderboard position can no longer be explained by pointing at his sessions — and explicability is the property on which the whole motivation layer depends.
Commitment 2 — authorisation is decided in one place The boundaries of what each role may see are defined once, in app/scope.py, and every endpoint asks that module rather than re-deriving the rule. The alternative — patching each endpoint — was tried and failed: the leak returned with the next endpoint added. Correspondingly, an empty scope returns None, never {}, because an empty MongoDB filter means “everything”, which is the exact inversion of the intent and the kind of bug that looks correct while it leaks.

1.6 Contributions of the work

  1. A weighted, closed error taxonomy for recitation. Four error classes with numeric severity weights, storing the class code and never the weight, so that recalibrating the weights retroactively corrects all historical data (§9.2).
  2. Quality-sensitive completion forecasting. A model in which the projected date responds to how well a student recites, not only how much — with domain sign constraints applied to the fitted coefficients so that the system can never tell a parent that their child's errors are accelerating his completion (§9.4).
  3. Multi-criteria motivation. Four separate leaderboards derived from the same session records as the metrics, with an append-only, idempotent experience-point ledger (§9.5).
  4. A single-source authorisation model with a proving test suite. Four scope levels resolved through one documented chain, guarded by 314 assertions that test for leakage of other people's data rather than for request success (Ch. 3, 13).
  5. A tamper-evident administrative record. Atomic sequencing, hash chaining, explicit gap marking and a never-purged class for money and permission events (§10.7).
  6. An engagement measure for supervisory bodies that is normalised by centre size, distinguishing a working centre from a large one (§9.6).

2.2 Out of scope

Table 2.2 — Explicitly excluded from this version
ExcludedRationale
Online payment processingFees and salaries are recorded, not transacted. No payment gateway, mobile-money integration or reconciliation with a bank is present. Introducing money movement changes the regulatory and security posture of the whole system and is a separate project.
Native mobile applicationsAn earlier Expo/React Native prototype was abandoned in favour of a web application installable as a PWA (§12.5). One code base, no store review cycle, and installation over HTTPS on Android, iOS and desktop.
Audio capture or automatic recitation assessmentNo recording, no speech recognition, no automated tajwīd scoring. The teacher's judgement is the input; the system structures it.
A Qur'anic text corpusThe system stores sūrah name and number and an āyah range as entered. It does not ship the Qur'anic text, nor a verse-level database of the 114 sūrahs, 30 ajzāʾ, 60 aḥzāb and 240 arbāʿ. Page counts are derived from āyah counts by a declared approximation (6,236 āyāt ÷ 604 pages) when not entered explicitly.
Email and SMS deliveryNotifications are in-application only, persisted and streamed. Password-reset codes are retrieved by an administrator through an authenticated endpoint rather than mailed; there is no SMTP or SMS provider integration.
Sponsorship and donation processingThe public /sponsorships page is a presentation prototype backed by hard-coded sample opportunities. It is not connected to any back-end endpoint, collection or payment path, and is documented here as a prototype, not a feature.
Timetable optimisationThe academic schedule is recorded as entered. There is no conflict solver, no room-allocation optimiser and no automatic generation.
Server-rendered PDF generationCertificates and student report sheets are produced by the browser's print pipeline from print-styled components, not by a server-side PDF service. CSV is the only server-generated export format.
Offline data entryThe service worker caches the application shell so the app starts without a network, but there is no offline write queue: recording a recitation requires connectivity.

2.3 Deliberate exclusions and their rationale

Three exclusions deserve separate treatment because they were considered, specified elsewhere, and consciously not carried into this system.

2.3.1 Teacher-generated student login codes

The research source for the analytical layer (§9.1) specifies student authentication by a short code that the teacher generates, as a solution for students without email addresses. Mishkaat instead issues each student a username and password through the centre manager, with a role and a permission scope attached. The code-based flow is not an improvement over an account that already exists, and altering the authentication path carries a security cost that is not justified by a need the system does not have.

2.3.2 A full English interface

An internationalisation layer existed and was used by five screens while the remaining text was Arabic in the source. A partial translation layer is worse than none: it produces an interface that is half-translated at runtime and gives a false impression of language support. The layer and its language picker were removed, and the interface is single-language Arabic. Completing a full translation is a broad mechanical task, independent of the analytical work, and deserves its own pass.

2.3.3 Timezone-aware timestamps

All stored timestamps are naive UTC. Python's datetime.utcnow() is deprecated, so the system routes every timestamp through app/clock.py, which returns the identical value with the deprecation removed. Migrating to timezone-aware datetimes is a data migration — every stored row and every comparison in the code base would have to change, or every comparison raises TypeError: can't compare offset-naive and offset-aware datetimes — and is recorded as future work (§16.3), not smuggled in as a function substitution.
