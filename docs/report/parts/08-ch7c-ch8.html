7.12 Indexing strategy

Seventy-one index definitions are declared in app/startup.py and created on every boot. Creation is idempotent and defensive: a definition that conflicts with an existing index of the same key (MongoDB error 85, IndexOptionsConflict) causes the old index to be dropped and recreated rather than aborting the boot, and a unique index that cannot be built because legacy duplicates exist logs an explicit warning and leaves the service running — activating the constraint would stop the whole deployment; the warning tells the operator to clean the duplicates and restart so that the guarantee becomes real.

7.13 Integrity, retention and deletion semantics

7.13.1 Referential integrity

References are string-encoded ObjectId values in ordinary fields. There is no cascading delete. Integrity is maintained by three mechanisms instead: (a) every write validates that the referenced document exists and lies inside the caller's scope before inserting — a competition judge must belong to the centre, an attendance record's student must belong to the named circle, a salary's teacher must belong to the paying centre; (b) deletion is predominantly soft, so dangling references do not arise; (c) reads tolerate a missing referent by rendering a placeholder rather than failing.

7.13.2 Three deletion semantics

Table 7.19 — Deletion semantics by record class
SemanticsApplies toBehaviour
Soft deleteRecitations, studentsis_deleted: true. The row survives for audit but leaves every metric, score, leaderboard and forecast. Filters are written {is_deleted: {$ne: true}} and never {is_deleted: false}, because historical rows do not carry the field at all and an equality test would hide every one of them.
VoidFees, salaries, expensesvoided: true with a mandatory reason, actor and time. The row is excluded from every total. Money is cancelled, never erased — and a void that did not also remove the amount from the sums would be a cancellation on screen and money still present in the figures.
Hard deleteAttendance rows, competition registrations, messages, certificates (revocation)Physical removal, always accompanied by an audit entry naming the actor and the removed record.

7.13.3 Retention

  • Never purged: audit entries for financial actions (fee collection, salary payment, expense creation and deletion) and for permission and credential actions (password changes and resets, centre registration, approval, rejection and status change). These carry no purge_at field.
  • Two years: all other audit entries carry purge_at = timestamp + 730 days.
  • 180 days: notifications, expired automatically by a TTL index on created_at.
  • Minutes to hours: every security collection, expired by TTL so that transient state cannot grow without bound in a long-running deployment.
  • Indefinite: all academic, financial and identity records, subject to the centre's own policy.

7.13.4 Normalisation posture

The schema is normalised where correctness depends on it and denormalised where display does. Error severity weights are the clearest case: the weight is not stored with the error. Only the class code is stored, and the weight lives in one module. This is a deliberate removal of a transitive dependency — the weights are declared provisional and will be recalibrated on real data, and had they been written alongside each error, recalibration could never repair historical records and the same error would carry different weights in different rows.

Conversely, names are denormalised freely: student_name on a recitation, teacher_name on a circle, halaqah_name on a student, center_name on a certificate. These are display copies on records that are already historical — a certificate should print the centre name as it was at issue — and they remove a join from every list view. center_id is copied onto recitations, attendance and fees for the same reason: it converts a two-collection scope query into a single indexed lookup.

Chapter 8API Specification

8.1 Conventions

  • All endpoints are prefixed /api and exchange JSON, except the login form (multipart), file upload (multipart), CSV export (text/csv), logo retrieval (image) and the notification stream (text/event-stream).
  • Authentication is a bearer access token in the Authorization header. Only the refresh endpoint relies on a cookie. Unauthenticated endpoints are exactly five: health, readiness, public centre registration, the public best-centres listing, and login.
  • Scope is applied server-side to every list endpoint. A query parameter may narrow within the caller's scope; it can never widen it. Passing ?halaqah_id= or a path identifier outside the caller's scope returns 403, not a filtered 200.
  • List endpoints accept limit and skip where volume warrants it, with server-enforced ceilings.
  • Every identifier supplied by a client is converted through safe_object_id, which returns HTTP 400 for a malformed value rather than allowing a 500.
  • Interactive OpenAPI documentation is served at /api/docs in development and is disabled entirely — schema included — in production.
