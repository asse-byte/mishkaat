Chapter 5System Architecture

5.1 Architectural style and rationale

Mishkaat is a modular monolith: one deployable back-end process, internally decomposed by domain into routers over a shared set of cross-cutting modules, serving a decoupled single-page front end over a JSON API. The choice is deliberate and is defended here because it is the architectural decision with the widest consequences.

Table 5.1 — Architectural options considered
OptionWhy it was not chosenWhat was chosen instead
MicroservicesThe expected deployment is a single modest VPS run by one operator. Splitting eleven domains into services would multiply the operational surface — service discovery, distributed tracing, cross-service authorisation — for a system whose entire authorisation model depends on being decided in one place.One process, domain-separated routers, one authorisation module.
Server-rendered templatesThe interface needs to be installable, work from a cached shell, and re-render live analytics without full page loads.A JSON API plus a SPA delivered as a PWA.
A synchronous WSGI frameworkMost endpoints are I/O-bound aggregations over MongoDB, with a live notification stream held open per connected user. Thread-per-request scales poorly for held-open connections.ASGI (FastAPI + Uvicorn) with an async MongoDB driver end-to-end.
A relational databaseThe academic record is naturally document-shaped and evolves: a recitation gained page counts and an error-tag map without a migration; judge scores are an array inside a contestant.MongoDB, with integrity enforced by unique and partial indexes where it matters (§7.13).

5.3 Deployment view

The reference deployment is the Docker Compose stack shipped with the repository. Its defining property is that only Nginx is reachable: the application publishes no port and MongoDB publishes no port; both sit on a Docker network declared internal: true, which also denies them outbound internet access.

Internet │ 443/tcp (TLS) ┌────────────▼─────────────┐ │ nginx:1.27-alpine │ networks: public + internal │ TLS · HSTS · CSP │ volumes: nginx.conf, ops/tls (ro) │ rate-limit · body cap │ 80 → 301 → 443 └────────────┬─────────────┘ │ proxy_pass → app:8001 (X-Forwarded-For set here) ┌───────────────▼──────────────────────────┐ │ app (backend/Dockerfile) │ network: internal only │ uvicorn, UVICORN_WORKERS=4 │ read_only: true │ APP_ENV=production, TRUST_PROXY=true │ tmpfs: /tmp │ no published port │ cap_drop: ALL └───────────────┬──────────────────────────┘ no-new-privileges │ mongodb://app-user@mongo:27017/?authSource=… ┌───────────────▼──────────────────────────┐ │ mongo:7.0 --auth --bind_ip_all │ network: internal only │ volume mongo_data │ no published port │ ops/mongo-init.js → scoped app user │ healthcheck: ping └──────────────────────────────────────────┘
Why TRUST_PROXY is true here and false by default The rate limiter keys on the client IP. Behind a proxy, the socket peer is the proxy for every user, so five bad passwords from one person would lock out every user of the deployment. The fix is to read X-Forwarded-For — but only when the application is genuinely behind a proxy under the operator's control, because trusting that header blindly lets any client forge it and evade the limiter altogether. In the Compose stack the app has no published port and Nginx sets the header itself, so the flag is safe; the shipped default in .env.example is false.

A second supported topology runs the same components directly on a VPS under systemd. The mishkaat.service unit runs the API under DynamicUser with NoNewPrivileges, no write access outside /tmp, no access to kernel tunables, and an outbound network allow-list restricted to localhost. A companion timer unit runs the encrypted backup daily (§14.3).

5.6.1 Token handling in the client

The access token lives in a module-scoped variable — not in localStorage — so it disappears when the tab closes and is never readable by injected script. The refresh token is never seen by JavaScript at all: the server sets it as an httpOnly cookie scoped to /api/auth with SameSite=lax, and the browser attaches it automatically. Session persistence across a page reload is preserved by calling /api/auth/refresh on boot with no body: the cookie alone re-establishes the session.

A single-flight guard wraps refresh. Because the server rotates the refresh token and revokes the previous one, two concurrent refreshes would invalidate each other and log the user out; concurrent 401s therefore await one shared refresh promise. A 403 is never treated as session expiry — it is a permission shortfall, and logging the user out on one would be both wrong and confusing.

5.8 Recurring design patterns

Table 5.5 — Patterns used consistently across the code base
PatternApplication
Single gateEvery endpoint accepting a student_id passes it through check_student_access, never through a hand-written center_id comparison. One hole in the gate previously produced ten leaks; one fix closed all ten.
Fail closedAbsent assignment means denial. An empty scope returns None; a manager with no center_id sees nothing rather than everything.
Identity from the tokenThe acting user is taken from the verified token, never from a request field. This removed a class of both bugs and forgeries: the client used to send the account ID where the teacher-record ID was expected, so every teacher's recitation was refused.
Compute on readNo derived academic value is stored. Metrics, ranks and forecasts are functions of the session records at the moment of the query.
Constraint in the databaseWhere duplication must be impossible, a unique (often partial) index enforces it. An application check followed by a write is not atomic — two simultaneous clicks both find nothing and both insert.
Idempotent side effectsXP awards carry a unique (student, reason, source) key; a duplicate-key error is treated as success, not failure.
Bulk over per-rowAggregate screens load their history in one or two queries keyed by an $in list, rather than a query per student.
Soft delete and voidAcademic records are soft-deleted with is_deleted; money is voided with a reason and an actor. Both filters use $ne: true so that historical rows lacking the field are still visible.
Configuration over constantsCalibration values — severity weights, smoothing, windows, XP rates — live in config.py and are environment-tunable, not buried inside a function.
Decision records in codeNon-obvious decisions are documented at the site of the code, stating what the previous behaviour was and why it was wrong. This report draws directly on those records.

6.5 Dependency policy

  • Every back-end dependency is pinned to an exact version. The runtime surface of this system includes cryptography and token handling; a floating version is an unreviewed change to security-relevant code.
  • The dependency list is deliberately short. Nine runtime packages. The forecasting model is implemented with plain Python arithmetic rather than pulling in a numerical stack, which keeps the image small and the audit surface narrow.
  • Vulnerability scanning is specified as a CI gate (pip audit, build fails on critical findings), with a quarterly review of Python and MongoDB minor versions.
  • No third-party analytics or telemetry is included anywhere in the client, because the platform holds data about minors.
