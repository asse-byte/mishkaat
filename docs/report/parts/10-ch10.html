Chapter 10Security Engineering

10.1 Data sensitivity and threat model

Mishkaat stores the names, dates of birth, guardians' names, addresses and telephone numbers of children under eighteen, together with a continuous behavioural record of their attendance and academic performance, and the financial affairs of the centres that teach them. The security posture assumes the strictest applicable privacy regime, and security requirements are treated as functional requirements rather than as deployment hardening.

10.2.1 The five verification checks

Every authenticated request performs all five, in order:

  1. Signature and expiry verification (HS256).
  2. Token type must be access.
  3. The JTI must not appear in revoked_tokens.
  4. The account must exist and be active — otherwise 403, so that deactivation takes effect on already-issued tokens.
  5. The token's uv must equal the account's current user_version, and its iat must not precede password_changed_at.

Checks 4 and 5 are what make a password change a genuine global logout rather than a local one.

10.2.2 Client-side session handling

Session persistence across a reload relies on the cookie alone: at boot the client posts an empty body to /api/auth/refresh. A single-flight guard ensures concurrent 401s trigger one shared refresh — because the server rotates and revokes, two parallel refreshes would invalidate each other and eject the user. A 403 is never treated as expiry; it is a permission shortfall, and logging the user out on one was a defect that has been removed.

10.3 Authorisation architecture

Authorisation is applied in four layers, and no layer is sufficient alone.

Table 10.3 — Authorisation layers
LLayerMechanismWhat it stops
1Role gateAn explicit role allow-list at the top of a handler; teacher_only() for attesting actions.A guardian calling a finance endpoint; a manager recording a recitation.
2Scope filterscope.student_query, visible_student_ids, visible_halaqah_ids applied to the query itself.A list endpoint returning rows outside the caller's centre or circle.
3Ownership gatecheck_student_access(student_id) on every endpoint that takes one.Direct object reference: guessing or enumerating another student's identifier (BOLA / IDOR).
4Field redactionredact_teacher and equivalent response shaping.Salary and marital status reaching a student, guardian or colleague inside an otherwise legitimate response.
Three rules that are not to be broken 1. check_student_access is the only gate for any endpoint taking a student_id. It is never bypassed with a hand-written center_id comparison — one hole in it previously produced ten separate leaks.
2. An empty scope returns None, never {}. An empty MongoDB filter means everything, the exact inverse of the intent, and it reads as correct code.
3. A path or query parameter narrows within the scope or returns 403. It never widens it.

10.4 Credential policy and recovery

  • Hashing: bcrypt at cost 12, tunable upward by environment.
  • Complexity: at least eight characters, including a letter and a digit, enforced uniformly on every path that sets a password — self-service change, teacher account creation, manager account creation, public registration, student and guardian issuance, and administrative reset.
  • Issued passwords are generated from an alphabet that excludes visually confusable characters (O/0, l/1/I), because they are written on paper and handed over. They are shown exactly once and stored only as a hash. A forgotten password is replaced, never recovered, and the replacement bumps user_version, closing open sessions.

10.4.1 The reset flow

  1. A reset request is rate limited on both the requesting IP and the target account: five per hour each.
  2. A code is generated and stored as HMAC-SHA256(secret, "username:code") — never in plaintext, and bound to the username so that a code for one account cannot be used on another. Any plaintext code field left by earlier versions is actively removed on write.
  3. The record expires after ten minutes by TTL index, and five wrong attempts invalidate it.
  4. Responses are identical whether or not the account exists, so the endpoint cannot enumerate accounts.
  5. A successful reset bumps user_version, clears the account lockout, and writes a permanent audit entry.

All limiter state lives in MongoDB with TTL indexes, so it is correct across worker processes and cannot grow without bound. The earlier in-process dictionary was both incorrect with multiple workers and an unbounded memory leak. Client IP resolution honours X-Forwarded-For only when TRUST_PROXY is set, because trusting the header unconditionally lets any client forge it.

10.6 Personal data protection at rest

Three student fields are encrypted with Fernet (AES-128-CBC with HMAC-SHA256) before being written: date_of_birth, guardian_address and parent_name. Decryption tolerates legacy plaintext, so enabling encryption on an existing database does not break reads.

Why phone numbers are deliberately not encrypted Phone numbers back the ownership matching in check_student_access and the guardian lookup used to send an absence alert. An encrypted field cannot be queried by equality, so encrypting them would break authorisation itself. This is a documented, bounded trade-off rather than an omission.

Two operational consequences follow, and both are stated in the deployment documentation: the key must be in a secret manager rather than only in an .env file, and losing it destroys those fields permanently — decrypt_pii tolerates plaintext, but not a wrong key. Key rotation requires a one-off re-encryption pass, which must be planned before it is needed.

10.7 Tamper-evident audit logging

Thirty-five action types are recorded (Appendix B). Each entry is linked to its predecessor:

hn = SHA-256( seq ∥ actor_id ∥ center_id ∥ action ∥ canonical(payload) ∥ timestampISO ∥ hn−1 ) with canonical(payload) a JSON serialisation with sorted keys, and h₀ = 64 zeros. Altering any field of any entry breaks every subsequent hash.

Three details make the chain sound in practice rather than only in principle:

  • Atomic ordering. The sequence number comes from an atomic counter, and the chain is built on that order. Reading the predecessor by sorting on timestamp meant two simultaneous writes obtained the same predecessor hash, splitting the chain silently and causing later verification to report tampering with no discoverable cause.
  • Millisecond truncation. Timestamps are truncated to milliseconds before hashing, because MongoDB stores only millisecond precision. Hashing microseconds would make every recomputed hash differ from the stored one and report tampering in a perfectly sound record.
  • Explicit gaps. When a predecessor cannot be resolved — after a short retry window that allows for concurrent writes from another worker — the entry is written with chain_gap: true. The record states the break rather than pretending the chain is intact.

GET /api/audit-logs/verify recomputes every hash from the stored fields and reports mismatches and marked gaps. Financial and credential actions carry no purge_at and are never removed; all other entries expire after 730 days.

10.8 File upload security

Table 10.6 — Upload controls

CORS allows an explicit list of origins with credentials enabled; a wildcard origin aborts the boot in production, because a wildcard with credentials is a contradiction. The origin list is whitespace-trimmed — a correctly written "a, b" configuration previously kept the space attached to the origin and silently blocked the real front end. Nginx adds an independent header set, an HTTP→HTTPS redirect, a client_max_body_size cap and an optional edge rate-limit zone on the login path as defence in depth.

10.10 Fail-fast production guards

The application refuses to start in production if any of the following holds. Each condition was chosen because the alternative is a silently insecure deployment that appears to work:

Table 10.8 — Boot-time refusals
ConditionWhy the boot is aborted
SECRET_KEY is still the built-in defaultEvery token in the deployment would be forgeable by anyone who has read the source.
PII_ENCRYPTION_KEY is unsetChildren's personal data would be written in plaintext. In development an ephemeral key is generated with a warning that the data will not survive a restart.
ALLOWED_ORIGINS contains *A wildcard origin with credentials enabled exposes every authenticated endpoint to every site.
INITIAL_ADMIN_PASSWORD is unset while bootstrapping the administratorOtherwise the most powerful account would be created with a predictable password.
INITIAL_SUPER_ADMIN_PASSWORD is unset while bootstrapping the super-administratorThis account sees and suspends every centre. It previously fell back to a fixed string whenever the administrator password was unset — including in production, because the earlier guard checked only the administrator account and was skipped entirely if that account already existed. The two accounts now also take separate passwords, so that a leak of one is not a leak of both.
