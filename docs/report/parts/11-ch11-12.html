11.2 Enrolment and account issuance

Enrolment and account issuance are deliberately separate steps. The student record is created first; accounts are issued afterwards, by the manager, and bound to the record by identifier.

  1. Enrol. POST /api/students with guardian details, memorisation plan and circle. Date of birth, guardian name and address are encrypted before writing. The circle's occupancy count is updated.
  2. Issue accounts. POST /api/students/{id}/accounts creates an account for the student, the guardian, or both. Each password is generated from an alphabet without confusable characters, returned exactly once so the manager can hand it over, and stored only as a hash. The account identifiers are written to students.user_id and students.parent_user_id, so the binding survives a change of phone number. The issuance is audited.
  3. Replace, never recover. POST …/accounts/reset issues a new password for one holder. There is no retrieval path — and the reset bumps user_version, closing that holder's open sessions on every device.

11.3 The daily recitation cycle

teacher opens the recitation screen │ ├─ students listed = scope(teacher) = his circles only ▼ enters sūrah · āyah range · type (new | review) · pages? · error tags · evaluation │ ▼ POST /api/recitations ┌────────────────────────────────────────────────────────────────────┐ │ 1. teacher_only() manager/admin → 403 │ │ 2. check_student_access() not his circle → 403 │ │ 3. teacher record resolved FROM THE TOKEN (not from the body) │ │ 4. duplicate check on (student, type, date_str) → 409 if present │ │ 5. insert with date, date_str and center_id │ │ 6. side effects, none of which may fail the write: │ │ • XP: 10 × pages, keyed by the recitation id (idempotent) │ │ • badge re-evaluation against the fresh snapshot │ │ • invalidate the centre's cached forecast model │ └────────────────────────────────────────────────────────────────────┘

Step 6 is wrapped so that a failure in the motivation layer is logged and ignored: the session is the real record and the points are a layer above it. Binding their fate together would mean a teacher loses their work because of a defect in gamification.

Corrections are first-class. The recording teacher may edit or soft-delete their own session; centre administration may correct any session in the centre. A soft-deleted session leaves every metric, score and forecast, but remains in the database for audit.

11.4 Attendance and absence notification

teacher submits the roll for a circle and a date │ ▼ POST /api/attendance (records[], date) per record: student exists · student belongs to this circle · circle belongs to this centre → otherwise 403 │ ▼ upsert on key (student_id, date_str) │ ├─ inserted → "created" │ └─ matched → "updated" ← what a teacher correcting a mark expects │ (a DuplicateKeyError from a simultaneous double-click is caught and │ retried as an update, so the correction is not lost to a 500) ▼ status = absent ? ├─ no → XP: 5 points, source key "student:date" (idempotent across re-submission) └─ yes → guardian resolved by parent_phone → notification PERSISTED ("absentee_alert" with the student, the date and the circle) and only then streamed

Two defects shaped this design. First, the roll was inserted rather than upserted, so re-submitting it — a double-click, or a teacher correcting an absence to a presence — created two contradictory rows for the same student on the same day, and the absence stayed in the attendance rate forever. Second, the alert was streamed only, so it reached a guardian who happened to have the application open at the moment the roll was taken. Persisting first and streaming from the database fixed both the reachability problem and a multi-worker problem: with four workers, an in-process fan-out reached only the quarter of users connected to the worker that wrote the event.

Table 11.1 — Competition marking scheme
CriterionMaximumNotes
Memorisation (الحفظ)70Each judge's total is the sum of the three. The contestant's score is the arithmetic mean of the judges' totals, and the number of judges who have marked is reported alongside it. Re-marking replaces only that judge's entry.
Tajwīd (التجويد)20
Voice (الصوت)10

Three rules are absolute here. Branches are ranked separately, each from position one, so a memoriser of Juz' ʿAmma is never placed at the bottom of a list headed by memorisers of the whole Qur'an; and the branch list is closed, because free text would make results impossible to aggregate or archive across centres. Every mark is attributed: previously a single score sat on the contestant, so the last judge to open the screen silently erased his colleague's marking and no one could tell who had given what. Administration does not mark — the manager appoints the panel and approves the outcome; recording a mark is testimony from someone who listened.

Finally, judging is a task with a term, not a standing permission: the competitions menu item appears for a teacher only while a competition they judge is in progress, and disappears after approval. The hiding is in the interface; the prohibition is on the server.

11.6 Certificate issuance

Table 11.2 — Milestones
CodeMilestonePartsPages required
juz5Five parts memorised5≈ 100.7
juz10Ten parts memorised10≈ 201.3
halfHalf the Qur'an15≈ 302.0
khatmThe whole Qur'an30604

Issuance is restricted to the centre manager, and three conditions apply:

  1. It is a recorded act, not a print button. Each certificate carries a serial (MK-YYYY-NNNNN, allocated from an atomic counter per centre per year), the issuer's identity and the issue time. A certificate that is later questioned can be traced; and it cannot be printed twice without anyone knowing.
  2. It is never issued twice. Partial unique indexes enforce one milestone certificate per student per milestone and one competition certificate per contestant. A code check before a write succeeds twice when the button is pressed twice simultaneously.
  3. It is never issued early. A milestone certificate is refused with 409 until the pages actually recited reach the threshold (with a half-page tolerance), and the refusal states how far the student has reached. A competition certificate is refused until the results are approved — a certificate bearing a score that can still change is a document that cannot be trusted.

Revocation exists, for a wrong name or a wrong milestone, and is audited exactly as issuance is. Students and guardians see and print their own certificates; only the manager issues them.

11.7 Financial operations and the void policy

create ──► amend ──► collect/pay ──┐ │ │ │ │ │ ▼ │ │ [409 if already paid] │ ▼ │ every administrative act is fallible, so every one is correctable ▼ VOID (never delete) ├─ voided = true ├─ void_reason = written reason (required) ├─ voided_at = timestamp ├─ voided_by = actor └─ EXCLUDED from every aggregate: {voided: {$ne: true}} — marking without excluding would be a cancellation on the screen and money still present in the figures │ ▼ permanent audit entry (no purge_at — kept forever)

The void filter is written {voided: {$ne: true}} rather than {voided: false} because historical rows do not carry the field at all, and an equality test would silently drop every one of them from every total.

11.8 Messaging

The chain of §3.5 is enforced on the server and published by GET /api/messages/audiences; the client never contains its own copy of the rule. Attachments are uploaded first — returning a descriptor — and then referenced when the message is sent, which is simpler than mixing a payload with a file in one request and allows the sender to change their mind before sending. A sent message can be corrected (the edit is visible as such) or withdrawn.

The design was driven by two concrete failures: a system administrator could not send a single message, because the handler required a centre and the administrator account has none, while the interface displayed the full set of broadcast controls; and a centre manager had no route to system administration at all.

Table 12.5 — Installation by platform

HTTPS is mandatory: browsers offer installation only over a secure connection (or localhost). The manifest declares standalone display, an RTL Arabic locale, a dark theme colour and shortcuts to the most frequent tasks. All icons are generated from a single vector source by a build script.

Two operational rules for the PWA (1) The displayed name comes from short_name in the manifest on Android and desktop, and from apple-mobile-web-app-title in the HTML on iOS. Changing one without the other gives a different name on different devices. iOS shows roughly twelve characters and then truncates, which is why the iOS title is the short form alone.
(2) The service worker caches the application shell under a versioned cache name. Changing any icon requires bumping that version, or installed devices keep showing the old icon indefinitely. The shell is cached asset by asset rather than atomically, so one missing file cannot block the entire update.

12.6 Printing and document output

Certificates, student report sheets and centre reports are produced through the browser's print pipeline from print-styled components, with a landscape helper for wide tables. One rule governs all of them: printed output uses fixed colour values, never design-system tokens. Tokens invert under the dark theme, so a user printing in the evening would receive pale text on white paper. CSV exports are written as UTF-8 with a byte-order mark, because Excel otherwise opens them in the wrong encoding and renders Arabic names as symbols.
